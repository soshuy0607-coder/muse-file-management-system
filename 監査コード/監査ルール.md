# ファイル管理・監査のルール詳細

ファイル置き場の管理ルールと監査システムの詳細は、すべてこの文書に集約する。
全体用 AGENTS.md には核と案内だけを置き、詳細はここに置く。

**読み方（大切）**：この文書は「必要なときに、必要な節だけ」読むためのもの。
毎回全体を読まないこと。まず下の目次で当たりを付け、該当する節だけを開く。

## 目次

1. 構成 — 監査コードフォルダの中身と役割
2. 実行 — 監査の回し方
3. 監査ルール（全15項目） — 監査が確認する内容の一覧
4. ファイル管理の詳細 — プロジェクトの置き方・台帳・担当ゴールの紐付け
5. ゴール置き場の詳細 — goals/ の構造とゴール名フォルダ
6. 変更するときの注意 — コードや書式を変えるときの決まり
7. 本棚システムの設計 — 毎回読まれるファイルの「核＋目次」化

## 1. 構成

- `audit_file_storage.py` — 入口。全体の照合（一覧・ゴール）と実行・報告を担当
- `監査ルール.md` — このファイル。ルールの詳細
- `checks/` — 分割した部品
  - `audit_common.py` — パス・定数・結果の入れ物（Results）・小さなヘルパー
  - `audit_check_project.py` — プロジェクト単体のチェック
  - `audit_cross.py` — 一覧の読み取りとプロジェクト情報の収集
  - `audit_shelf.py` — 本棚の照合（カタログの目次と棚フォルダ）

直下に置くのは入口と 監査ルール.md のみ（監査ルール13で自身も監査する）。
部品を増やすときは直下ではなく `checks/` の中に入れること。

## 2. 実行

```
python3 ~/workspace/監査コード/audit_file_storage.py
```

既定は要約表示：OKは集約して出し（プロジェクト個別チェックは
「命名 n/N件、チャット名 n/N件、担当ゴール n/N件」の1行）、エラーと警告は
全件出す。プロジェクトが増えても出力量はほぼ一定に保たれる。
OKの全行を見たいときは `--verbose` を付ける。

定期実行（運用例）：週1回程度のスケジュール実行と、ファイル構成に触れる
活動（プロジェクトの作成・改名、本の登録、台帳の更新など）の締めの実行を
組み合わせるとよい。いずれも正常時は報告せず、報告するのは
WARN / ERROR があるときだけとし、自動で直しはしない（報告のみ）が推奨。
別の方式として、約12時間おきに起きて「日次メモが直近12時間以内に
更新されているときだけ監査を回す」ゲート方式もある。日次メモは
全チャットの活動を集約するため、他のチャットでの構成変更も拾える。

管理用プロジェクトを置く場合は、その `files/` に入口へのリンクを置くと、
プロジェクト側からも実行できる（リンク先の実体で動く）。

## 3. 監査ルール（全15項目）

1. workspace/ 直下にファイルは置かない。
2. projects/ 直下のファイルは PROJECT_LIST.md だけを許可する。
3. プロジェクトフォルダ名は「プロジェクト名_テーマ」形式にする。
4. 各プロジェクトに INDEX.md / chat.json / files/ / inputs/ / hidden_files/ があること。
5. プロジェクト直下のファイルは INDEX.md と chat.json だけを許可する。
6. INDEX.md に「プロジェクト名：」「サイドチャット名：」「チャットID：」が書かれていること。
7. チャット名がフォルダ名と一致すること（INDEX記載、chat.json の実際のチャット名、chat_id を照合。チャット名を変更したら chat.json も更新すること）。
8. final / new / コピー などの曖昧なファイル名を使わないこと（警告）。
9. PROJECT_LIST.md と実態の双方向照合（実在するのに一覧に無い、一覧にあるのに実在しない、名前・IDの不一致はエラー。メインチャットは対象外）。
10. 担当ゴールの一致（一覧と INDEX を、ゴールIDをキーに集合として照合。書式は「ゴール名（ゴールID）」、複数は「；」区切り、無しは「なし」。ゴール名にプロジェクト名は埋め込まない）。
11. ゴール側の担当プロジェクト表記（GOAL.md の「担当プロジェクト：{…}」が割り当て実態と一致すること）。
12. ゴール名フォルダ（goals/<slug>/ の中にゴール名フォルダがあり、その中の GOAL.md が本体と同一であること）。
13. 監査コードフォルダ自身の構成（直下は入口と 監査ルール.md のみ、部品は checks/ の中。中身はPython部品のみ。Git管理物 `.git` / `.gitignore` はバージョン管理の仕組みそのものとして例外許可）。
14. 全体用 AGENTS.md のサイズが上限（3,000文字）以内であること（警告のみ。超えたら詳細をこの文書へ移す）。
15. 本棚の照合（「本棚フォルダ：」宣言のあるカタログについて、目次と棚フォルダの中身の双方向一致、リンク切れ・節の不在・実体の二重登録が無いこと。第7節）。

判定：エラーが1つでもあれば「問題あり」で終了コード 1。警告は 8 と 14。

## 4. ファイル管理の詳細

### 置き場所
- workspace/ 直下にファイルは置かない（例外なし）。
- 監査システムは専用フォルダ `workspace/監査コード/` に置く（構成は第1節）。
  管理プロジェクトの `files/` に入口へのリンクを置く。
- 1プロジェクト＝ `workspace/projects/` の下の1フォルダ。名前は
  「プロジェクト名_テーマ」（スペースは除く）。

### プロジェクトの作り
- 紐づくサイドチャットの名前は、フォルダ名と完全に一致させる。
- フォルダの中身は固定：`files/`（完成品だけ）、`inputs/`（資料・素材）、
  `hidden_files/`（下書き・中間ファイル）、台帳 `INDEX.md`（プロジェクト名・
  チャット名・チャットIDを記載）、実際のチャット名の控え `chat.json`。
- `projects/` 直下のファイルは `PROJECT_LIST.md` のみ（プロジェクト名・
  チャット名・チャットID・担当ゴールの一覧）。
- 終わったプロジェクトは削除せず `projects/_archive/` へ移す。
- 配置は `workspace/goals/<slug>/` と揃えてあり、プロジェクトをゴールへ
  そのまま昇格できる。

### 一覧と台帳の照合
- 監査は一覧を、実在フォルダと各プロジェクトの INDEX.md / chat.json と
  双方向に照合する。一覧に無いプロジェクト／チャットがある、または
  一覧にあるのに実在しない場合はエラー。
- プロジェクトやチャットを作ったら、同じターンのうちに一覧へ行を足す。
- チャットを改名したら、同じターンのうちにそのプロジェクトの chat.json を
  チャット一覧から更新する（監査コード自体はアプリのチャット一覧を読めない）。
- メインチャットはプロジェクトを持たず、一覧では対象外と明記する。

### 担当ゴールの紐付け
- 紐付けはIDによる参照のみで行う。設計原則：どの実体の名前にも、他の実体の
  名前を埋め込まない（ゴール名にプロジェクト名を含めない）。1つのゴールに
  複数プロジェクト、1つのプロジェクトに複数ゴールが割り当てられ得る（多対多）
  ため、名前への埋め込みは依存の逆転を招く。
  （フォルダ名＝チャット名は例外。これは依存ではなく、同一プロジェクトの
  表と裏であるため。）
- 担当ゴールは2か所に書く：一覧の担当ゴール欄と、プロジェクト INDEX.md の
  担当ゴール。書式は「ゴール名（ゴールID）」、複数は「；」区切り、
  無い場合は「なし」。監査はゴールIDをキーに集合として一致を確認する。
- 一覧性を高めるため、ゴール側には担当プロジェクトを集合で書く：
  ゴールの説明文と GOAL.md に「担当プロジェクト：{プロジェクト名, …}」。
  これは表示専用で参照キーではない。割り当てが変わったら両方を同期させ、
  監査が GOAL.md の集合と割り当て実態（各 INDEX から導出）の一致を確認する。

## 5. ゴール置き場の詳細

- `workspace/goals/<slug>/` はシステム管理。slug は自動採番の不透明な名前で、
  変えるとゴール記録の置き場対応や配下のシステムフォルダ
  （briefs、crons、references など）が壊れるため、改名・移動しない。
- `GOAL.md` は `goals/<slug>/GOAL.md` が定位置（本体）。
- 人間が読みやすい入口として、ゴール置き場の中にゴール名フォルダがあり、
  その中の GOAL.md は本体へのリンク（コピーではない）。
- 監査ルール12がこの構造を確認する。ゴール表記の走査は `goals/*/GOAL.md`
  だけを読むため、内側のリンクが二重に数えられることはない。

## 6. 変更するときの注意

- ルールを足すときは、該当する部品ファイルだけを読み・直す（全体を読まない）。
- 台帳の書式（PROJECT_LIST の列、INDEX の項目名）を変えたら、読み取り側
  （checks/audit_cross.py など）もセットで直す。
- 結果は必ず Results オブジェクト（audit_common.py）経由で集める。
  部品ごとにリストを持ち直さない。
- ROOT は audit_common.py が自分の場所から逆算する（環境変数 MUSE_AUDIT_ROOT
  で上書き可）。開始時に validate_root() が構成を確認し、想定と違えば
  「問題なし」と誤報せず中止する。部品の置き場所の深さを変えたらここも直す。
- 入口で sys.dont_write_bytecode を有効にし、__pycache__ を作らない。
- 変更後は必ず、正常系でエラー0になることと、わざとずらした負例で
  エラーになることの両方を確認する。
- 定期タスク（スケジュール実行）は現状では監査対象外（既知の限界：
  週次監査そのものが消えても監査は気づけない）。ここへ雑にチェックを
  足すと後で苦労するため、追加する場合は事前に設計を詰めること。
  論点：スケジュールファイル名には時刻キーが含まれ変わりうること、
  置き場は実行環境の管理下にあり配置がこちらの約束事ではないこと、
  存在判定の方法と誤検知の回避。
- トラッキング（見届け台帳）も監査対象外とする
  （既知の限界として定期タスクと同列に扱う）。理由：状態はシステム側の
  仕組みが管理し、一覧への問い合わせ自体が正であるため、「手管理の
  台帳と実態の照合」という監査の前提に合わないこと。作業場所が
  goals/<slug>/ をユーザーのゴールと共有するため、混ぜるとルール11・12が
  トラッキングをゴールと誤認しうること（対象化する場合は、まず両者の
  判別方法の設計が先）。将来、アイテムが増えて点検が必要になったら、
  ファイル監査への追加ではなく別建ての軽い点検（期限を過ぎても進行中の
  ままのもの、紐づくゴールの無いもの、完了したのに残っている定期
  チェックなど、意味的なズレの確認）として設計すること。

## 7. 本棚システムの設計

毎回読まれるファイル（AGENTS.md、USER.md、MEMORY.md など）が将来巨大化しても、
コストと管理性が悪化しないための仕組み。以下はその設計である。

### 考え方（3層）
- 核：毎回必ず読む部分。「知らないと判断を誤る」最小限だけを置く。短く安定させる。
- 目次：詳細への案内。1行1件で短く、何十件あっても軽い。背表紙として、
  本を開くべきか判断できる要約と合図を持つ。
- 詳細（本）：必要なときだけ開くファイル。内部も節で分かれ、該当節だけ読む。

### 建物と部屋
- 本棚フォルダは一か所に集める：ホーム直下の `~/本棚/`。
- 棚ごとの部屋を切る。部屋名はカタログファイル名と揃える（agents、user、memory など）。
- 部屋は最初から全部作らず、最初の本ができるときに作る。

### カタログ（入口ファイル）
- 毎回読まれるファイルがカタログになる。中身は「核＋自棚の目次」の2部構成。
- 目次の節の先頭に、自棚の宣言行を置く（例：`本棚フォルダ：本棚/agents`）。

### 目次の書式（システムが管理できる形）
- 1行1件、区切りは「 | 」、順序は固定：種別 | 題名 | 場所 | 要約 | 合図
- 種別は「本」または「参照」。
- 場所は棚フォルダ側のパス＋節名まで書く（例：本棚/agents/監査ルール.md#3. 監査ルール）。
- 1行形式にする理由：項目名の繰り返しが無くトークン効率が最良で、
  検索で該当の1行だけを抜き出せるため。

### 本と参照
- 本の実体は1か所だけ（主棚）。実物でもリンクでも、主棚の部屋に揃っていること。
  実物の置き場所は自由で、棚フォルダにはリンクを置いて揃える。
- 他の棚から使いたい本は、その棚の部屋にもリンクを置き、目次では「参照」とする。
  実体は複製しない（境界をまたぐ本は、主棚1つ＋参照で扱う）。

### 監査の役割（将来の拡張）
- 棚ごとに目次と部屋の中身を双方向照合：未登録、目次にあるのに無い、
  リンク切れ、参照先の節の不在を検出する。
- 実体の二重登録（2つの棚で「本」になっている）を検出する。
- 核のサイズ上限を警告で担保する（現行の AGENTS.md 上限警告の一般化）。

### 導入順（推奨）
1. まず1つの棚（例：agents）で型を作る。本は監査ルール.md が向く。
2. 残りの棚は、最初の本ができるときに部屋を作る。目次は空でよい。
3. システムが自動描画する索引ファイルへの宣言追加は、上書きされる
   恐れがあるため慎重に。扱いを決めてから入れること。

### 登録の例
- agents 棚：本＝監査ルール.md、参照＝ゴールの記録（実体は goals/<slug>/GOAL.md）
- memory 棚：本＝日次メモ、参照＝監査ルール.md
- 日次メモのように日々増える本は、新しいものができたら棚へ1件ずつ登録していく。
