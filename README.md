# ファイル管理システム 配布版 v1.0

AIアシスタント（Muse）のワークスペースが散らからないようにするための、
ファイル配置の規約と、それを自動で照合する監査スクリプトのセットです。
この配布物には設計とコードとテンプレートだけが入っており、実データや
個人の情報は含まれていません。

## 何を解決するか

- 置き場の直下にファイルが溜まっていく問題
- プロジェクトごとに置き方がばらばらになり、後から探せない問題
- 「毎回読まれる指示ファイル」が肥大化して、読むコストが増え続ける問題
- 規約があっても守られているか分からない問題（監査が照合する）

## 設計の要点

1. **直置き禁止**：`workspace/` 直下にファイルは置かない。例外なし。
2. **プロジェクトは自己完結**：1プロジェクト＝1フォルダ
   `projects/<プロジェクト名_テーマ>/`。台帳（INDEX.md）、チャット名の控え
   （chat.json）、成果物（files/）、資料（inputs/）、中間物（hidden_files/）を
   すべて内包し、紐づくチャットの名前はフォルダ名と完全一致させる。
3. **一覧は1つだけ**：`projects/` 直下のファイルは `PROJECT_LIST.md` のみ。
   監査が一覧と実態を双方向に照合する。
4. **紐付けはID参照のみ**：ゴールとプロジェクトの対応はIDで持ち、
   名前に他の実体の名前を埋め込まない（依存の逆転を避ける。多対多に対応）。
5. **核＋目次（本棚）**：毎回読まれるファイルは「核＋目次」の2部構成にし、
   詳細は棚フォルダの「本」に逃がす。目次は1行1件の固定書式で、
   機械的に照合できる。
6. **監査は静かに**：結果は要約表示で、項目が増えても出力はほぼ一定。
   正常時は報告せず、問題があるときだけ知らせる運用が前提。

## パッケージの内容

- `監査コード/` — 監査スクリプト一式とルール詳細
  - `audit_file_storage.py` — 入口
  - `checks/` — 照合部品（プロジェクト／一覧／ゴール／本棚）
  - `監査ルール.md` — 全ルールの詳細（必要な節だけ読む前提の文書）
- `テンプレート/` — 導入時にコピーして使う雛形
  - `PROJECT_LIST.md`、`INDEX.md`、`chat.json`
  - `AGENTS追記サンプル.md` — 全体用 AGENTS.md への書き加え例

## 前提環境

- Muse のような、ホーム直下に `AGENTS.md` 等の常時読込ファイルを持ち、
  `workspace/` と `workspace/goals/<slug>/GOAL.md`（`Goal ID:` 行を含む）を
  扱うアシスタント環境
- Python 3（標準ライブラリのみ。追加インストール不要）
- `chat.json` は、アシスタントがチャット一覧から書き写して維持する前提
  （監査スクリプト自体はアプリの状態を読めない）

## 導入手順

1. `監査コード/` を `~/workspace/監査コード/` に配置する。
2. `~/workspace/projects/` を作り、テンプレートの `PROJECT_LIST.md` を置く。
   `~/workspace/projects/_archive/` も作っておく。
3. テンプレートの `AGENTS追記サンプル.md` を参考に、全体用 `AGENTS.md` に
   核ルールと本棚カタログ（宣言＋目次）を書き加える。
4. `~/本棚/agents/` を作り、`監査ルール.md` へのリンクを置く
   （他の棚は、最初の本ができるときに作ればよい）。
5. 最初のプロジェクトを規約通りに作る：フォルダ＋同名チャット＋
   テンプレートから `INDEX.md` と `chat.json`＋一覧へ行を追加。
6. 監査を実行する：
   `python3 ~/workspace/監査コード/audit_file_storage.py`
   エラー0なら導入完了。
7. 任意：週1回のスケジュール実行を設定し、正常時は無報告・異常時のみ
   報告するよう指示しておく。終わりのない定期タスクの置き場として、
   完了させない恒久ゴール（いわゆる nullゴール）を1つ用意し、
   そこに所有させるのが推奨。

## 監査ルール（概要）

全15項目。詳細は `監査コード/監査ルール.md` の第3節。

- 直置き・命名・固定構成・台帳の必須項目
- チャット名＝フォルダ名の三方照合（台帳／chat.json／チャットID）
- 一覧と実態の双方向照合、担当ゴールの集合一致（IDキー）
- ゴール側の担当プロジェクト表記と割り当て実態の一致
- 監査コードフォルダ自身の構成、AGENTS.md のサイズ上限（警告）
- 本棚の目次と棚フォルダの双方向照合

## 既知の限界

- 監査は「実行した時点」の状態しか保証しない。定期実行と、構成変更時の
  実行を組み合わせることが前提。
- 定期タスク（スケジュール実行）とトラッキングは監査対象外。
  特に「週次監査そのものが消えた」ことは監査では検出できない。
  理由と、将来対象化する場合の論点は監査ルール.md 第6節にある。
- 台帳類は Markdown の書式に依存する。書式を変えたら監査コードの
  読み取り側も合わせて直すこと。
